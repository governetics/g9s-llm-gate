# D-001 — Артефакт llm-gate: единый compose-шаблон, passthrough, владение конфигурацией

**Дата:** 2026-11-04 · **Статус:** ACTIVE · **Сессии:** design 261104-01 (план),
impl 261104-01 (фазы 0–1; хранятся в доме проекта верстака)

## Контекст

Задача MVP: единый самодостаточный Docker-артефакт (LiteLLM + Admin UI + PostgreSQL),
поднимаемый одной командой локально и через панель governetics, с критериями: Claude
Code прозрачно работает через оба контура с боевыми Kimi/GLM; модели и credentials
администрируются через UI без правки YAML; fallback между провайдерами — на стороне
шлюза. До продукта стояли два критических неизвестных: (1) режим работы с
Anthropic-совместимыми провайдерами — native passthrough или unified-конверсия; (2)
аутентификация upstream — референс предупреждал, что при входящем клиентском
`Authorization` настроенный ключ провайдера upstream'у не уходит. Оба закрыты живым
спайком фазы 0 (capture-upstream контейнер, фиктивные ключи). Инварианты-вход: контракт
панели Path A и правила ключей, отработанные на g9s-mediapump D-002 (см. D-002 этого
проекта).

## Решение

**(а) Единый compose-шаблон на оба контура.** `deploy/compose.yml` — единственный
источник топологии: litellm `v1.108.0` + postgres `16.15` (пины минорных тегов),
секреты — пять ключей `LLM_GATE_*` (панель или `.env`), routing-политика — policy-YAML
через `configs.content` с hash-лейблом для пересоздания контейнера. Локальный и remote
контуры расходятся только значениями ключей.

**(б) Режим — native `/v1/messages` passthrough.** Anthropic-протокол проходит шлюз как
есть (`supported_endpoints: ["/v1/messages"]`); провайдеру уходит настроенный ключ
модели, не клиентский Bearer (capture-доказательство спайка; риск референса на v1.108.0
не воспроизвёлся). Конвертация протокола не выполняется вовсе.

**(в) Владение конфигурацией — один хозяин на область, dual-write запрещён.** Модели,
credentials (шифруются salt key), virtual keys и бюджеты → БД/Admin UI; routing-политика
(fallbacks, retries) и hardening → версионированный YAML. Публичные имена моделей —
семантические классы `top`/`optimal`/`fast`/`cheap`, набор живёт в БД и не заморожен
артефактом. Связка YAML-fallbacks → БД-алиасы подтверждена живьём (индуцированный отказ
primary → 200 от fallback-провайдера) — отдельный «вариант B» не понадобился.

**(г) Fallback — перекрёстный по классам, в YAML, только до начала ответа.** Топ-класс —
primary Kimi (качество рассуждений) с уходом на GLM; `optimal` — зеркально (экономия
Kimi-токенов); быстрая пара — аналогично. Mid-stream fallback — именованный предел.

Развилки оператора (план §9): №1 алиасы-классы — приняты как рекомендовано; №2 fallback
индивидуальный по провайдерам — принят; №3 владение моделями — БД/UI (вариант A) —
принят, gate фазы 1 на связку с YAML закрыт живьём.

## Отвергнутые альтернативы

- **Unified-конверсия** (`openai/…` / `anthropic/…` с конвертацией): лишний слой
  конвертации при провайдерах, уже отдающих `/v1/messages`; в спайке unified на
  Anthropic-входе v1.108.0 конвертировал в OpenAI Responses API (`/v1/responses`) —
  дополнительная поверхность расхождений без выгоды.
- **Вариант B — модели в YAML (`model_list`)**: нарушает владение (в) — сценарий «смена
  модели через UI без правки YAML» теряется, credentials пришлось бы тащить в env
  шаблона; БД осталась бы хранилищем только ключей. Держался как запасной на случай
  отказа связки YAML-fallbacks → БД-модели; связка подтверждена — вариант не нужен.
- **`[1m]`-алиасы в шлюзе** (серверные дубликаты моделей с суффиксом): двойная книга —
  живые пробы показали, что `[1m]` — клиентская нотация Claude Code (клиент вырезает
  суффикс до отправки; серверные ID провайдеров суффикса не знают, GLM отвечает 400
  «Unknown Model»). 1M-режим закрывается клиентскими env профиля.

## Последствия

- Смена/добавление модели — живьём через UI; артефакт не трогается. Обратная сторона:
  переименование алиаса тянет fallback-цели в YAML (иначе fallback молча теряет цель) и
  scope существующих ключей (UI-переименование обновляет scope; API delete+new — нет,
  ключ остаётся на старом имени → 403, лечится `/key/update`).
- Шлюз не знает про 1M-контекст: контекстные переменные — клиентская территория.
- Обновление LiteLLM = Prisma-миграции на старте: процедура «пин → бэкап → смена пина →
  проверка», никаких rolling-latest.
- Salt key не ротируется: потеря = потеря всех credentials; хранится с бэкапами БД.
- `PROXY_BASE_URL` в шаблон не входит: в v1.108.0 потребляется только SSO/OAuth-MCP,
  не нашим кейсом.

## Открытое

- A9 hardening remote-контура: перевод UI-логина с master key на DB-админа упирается в
  баг invitation/user-new в v1.108.0; план Б — env `UI_USERNAME`. Фаза 3.
- Приёмка фазы 3: полные CC-сессии через оба контура, индуцированный fallback на remote,
  изменение policy-YAML через панель, backup/restore живьём на ноде.

## Pre-conditions

- Спайк фазы 0: capture-доказательство upstream-auth (провайдеру уходит configured key);
  живые режим-пробы обоих провайдеров; факт серверных ID без `[1m]`; живой fallback по
  429.
- Решения оператора №1–№3 (план §9, 2026-11-04).

## Amendment 1 (2026-11-04): алиасы — роли слотов CC

Решением оператора (эксплуатация + внешние данные: GLM — терминальный агентный
кодинг и токен-дисциплина, Kimi — рассуждения/анализ/человекочитаемый текст;
единственный безоговорочный кейс Kimi — vision-ввод) классы
`top`/`optimal`/`fast`/`cheap` переименованы в роли CC-слотов:
`fable`=Kimi `k3.1-pro`, `opus`=GLM `glm-5.3`, `sonnet`=Kimi
`k3.1-pro-highspeed`, `haiku`=GLM `glm-5.3-flash`. Primary тяжёлого слота
перенесён на GLM; fallback перекрёстный по провайдерам — полный отказ одного
провайдера оставляет оба весовых класса обслуженными другим. Актуальная
таблица — architecture.md.


## Amendment 2 (2026-11-05): sonnet → GLM flash; полка swift

Решением оператора (Kimi highspeed даёт таймауты в лёгком контуре): `sonnet`
переведён на GLM `glm-5.3-flash` (дублирует `haiku`); Kimi highspeed сохранена
алиасом-полкой `swift` — цель fallback'а лёгких слотов (иначе модель осталась
бы неохваченной). Fallback: `sonnet`/`haiku` → `swift`, `swift` → `sonnet`.
